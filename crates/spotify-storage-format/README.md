# Spotify storage format foundation

Experimental storage support reconstructed and compared with Spotify for Windows 1.3.8.620. The application reads imported complete and partial audio, writes the native layout, and applies the verified storage policy to a separate working copy. Compatibility is scoped to this native build and the checks below.

Implemented primitives include index record validation and updates that preserve unknown fields, record encryption and decryption with an explicit key, payload transforms at arbitrary physical offsets, file IV and name construction, Adler32 checksums, preference value precedence, and capacity arithmetic.

Native comparison covers synthetic record encryption and decryption, synthetic payload transforms, and 161 capacity calculations. The fixtures contain public test keys and generated data, not the user's cache or account information.

`policy` provides the reference version's initialized capacity defaults, all 14 realm defaults, retention deadlines, and a pure eviction planner. It matches 350 native retention decisions and 254 native eviction plans, including equal deadline ordering, protected and open entries, realm quotas, total capacity, minimum ages, day rounding, and free disk space. The planner performs no deletions. Its specialized sorter follows Microsoft STL's algorithm with its license retained in `LICENSE-MICROSOFT-STL.txt`.

Cleanup rescheduling matches 128 calls to the native task scheduler: normally 10 minutes, 30 minutes after an empty pass with more than 512 MiB free, and 5 minutes below the free-space reserve. Read close bookkeeping matches 64 native cases, including a zero clock and saturation of the byte access counter. Writable playback readers persist their last-used timestamp and count at close; read-only imports do not change these fields. The server property `storage-size-config` parser matches another 128 native cases, including exact float percentage conversion and Windows integer overflow behavior.

`reader::Catalog` opens an explicitly selected snapshot with separately obtained storage state and validates every encrypted index record. Complete streams have bounded reads and seeks. Partial streams expose only checksum marked available ranges and reject reads of missing chunks. Both validate the footer, metadata, and each returned chunk. The application rejects decoder failures in memory without deleting imported files.

The playback adapter seeds its temporary download file from verified partial ranges and starts its first request at the first missing range. A local test reused 2,326,528 bytes, decoded and sought successfully, then fetched the remaining bytes and published the completed entry. All 23 partial files in the verification snapshot passed reads of their 10,494 available chunks (171,899,537 bytes).

`complete::write_complete` writes complete payloads, metadata, chunk checksums, and native footers into a caller supplied output stream. It reproduces the native encrypted or plaintext layout and preserves unknown footer fields. It does not open files, publish an index, or enable application cache writes. Local comparison reproduced all 656 complete files in a copied cache byte for byte (2,514,898,757 bytes and 153,617 chunks). These counts describe this verification dataset, not all Spotify caches.

`store::WorkingStore` publishes complete audio files and encrypted index records. It can create a new directory or exclusively open a distinct copy whose header matches an original opened read only. It rejects overlapping roots, index junctions outside the copy, and hard linked original indexes. Complete registered entries remain intact. The application completes partial entries in place using full range updates, preserving their filename, version, metadata, and existing encrypted chunks. The low level complete publisher also supports explicit version replacement. Failed writes stop further publication and retain unpublished files for inspection. Three completed entries, including an upgraded partial file, were retained by an isolated reference client.

The official client also played a complete entry written by Spotirust and sought to 30,896 ms with audio muted during verification. Its open storage stream referenced that exact indexed entry and marked it as read. After the test, the native filename and the 9,446,116 stored audio bytes had an identical SHA256. This verifies reuse of that written entry, beyond index acceptance; it does not establish coverage of every codec or all partial-download playback paths.

The application reads `%APPDATA%/Spotirust/storage-profile.json`, or an explicit `SPOTIRUST_STORAGE_PROFILE` override. The private JSON contains `snapshot_root`, `storage_key_hex` (32 hex characters), and `naming_state_hex` (40 hex characters). When no profile exists, a pasted cache in a supported location is initialized automatically by `spotify-storage-init`; see that crate's README for supported locations, the explicit setup command, and native version constraints. Keep private profiles outside version control. The snapshot is never passed to librespot's writable cache.

While importing, the player inherits supported streaming quality from the official account's user preferences. This prevents a 320 kbps cache from being missed because librespot otherwise defaults to 160 kbps. A full local player test, including its real output stage muted during verification, started cached playback and sought to 30 seconds with zero audio downloads. An offscreen application launch also loaded the default profile and matched the official 320 kbps setting.

An explicit `writable: true` enables experimental complete and incremental download callbacks into a separate working copy. Incremental writes preserve existing chunks, move the native trailer as the physical high water mark advances, and publish only whole downloaded chunks. A process restart reused 131,072 saved bytes and persisted another 65,536 bytes. The isolated reference client retained the resulting partial entry and counted its exact stored size. Concurrent readers can continue reading previously available chunks. Original file identity checks reject hard linked audio before any mutation. Failure to enable writes retains imported playback.

After authentication, writable profiles also run cleanup using the verified planner and timing. The worker uses the working volume's available and total bytes, local midnight, captured native capacity and realm overrides, and live `storage-size-config` updates from the authenticated session. An optional `configured_override` profile field records an active native byte limit; zero means automatic sizing. Reader leases register under the catalog lock so a cleanup pass cannot miss an opening track. The executor reproduces native index slot swaps and journals the changed records before removing guarded working files. Startup orphan cleanup considers only unregistered native filenames in matching data shards and retains unrelated files. Cleanup mutates only the separate writable copy. Before enabling the installed working profile, the Rust and native planners agreed that its 679 entries required zero removals.

A live worker test with six synthetic entries and a 1 MiB cap removed an expired entry and the next eligible capacity victim, while preserving an open track whose reader still returned the expected 16,384 bytes. An isolated official client also removed the expected expired synthetic entry. Storage preference and account property fingerprints trigger native settings recapture at startup and every 30 seconds while running. Writes and cleanup pause if settings cannot be verified. Runtime recapture was exercised with an open reader and an exclusively held index; playback remained available and writes resumed afterward. Editing copied INI preference files did not change the native active limit, so the integration captures active values rather than assuming those edits were applied. The realm override resolver also matches 64 native controls.

The working store uses a forward recovery intent for partial payload updates and index publication. It records only new encrypted bytes and changed index records, not a backup of previous audio. The intent is flushed before native files change, and is removed after data and index flushes succeed. On reopening a writable copy, replay happens before index parsing and checks the cache header, record checksums, and original file alias guards. Synthetic interruption tests cover partial data, a torn record, a torn appended record, and a completed transaction whose intent remains. Corrupted committed intents stop writes without changing native files. These are process interruption tests, not a claim of hardware power-loss guarantees.

Limits: initialization across other native versions, transient settings that never reach persisted source files, and native playback coverage for every codec and partial download path are unverified. The restricted initializer uses a clean native instance, so settings that exist only inside a running source process may differ. The official source cache is never passed to the cleanup executor. This does not claim universal equivalence with every Spotify release.

Run checks with:

```text
cargo test --manifest-path crates/spotify-storage-format/Cargo.toml
```
